# 体感ベース制御の設定 UI 設計書

作成日: 2026-07-30

制御ツール `auto-air-conditioner` が体感（不快指数）ベースの制御へ変わり、
`ac_control_rules` に 5 列増えて `fan_speed` が NULL 許容になった。この設計書は
ダッシュボード側の追随を扱う。

制御ツール側の設計は `auto-air-conditioner` の
`docs/superpowers/specs/2026-07-30-comfort-based-control-design.md` にある。

## 目的

増えた 5 つの設定を画面から編集できるようにする。あわせて、誤設定すると
挙動が逆になる `allowed_modes` の罠を UI とスキーマの両方で塞ぐ。

## 制御ツール側で何が変わったか

判定の軸が乾球温度から**実効目標温度**へ移った。湿度を織り込んで「同じ体感に
なる温度」を求め、それに対して運転を判断する。エアコンへ送る設定温度と風量は、
目標そのものではなく**目標を達成するための操作量**として目標から切り離された。

この分離がダッシュボードの画面構成に効く。目標を決める設定と、操作量を決める
設定は別の群になった。

## 追加・変更される列

| 列 | 型 | 既定 | 意味 |
|---|---|---|---|
| `base_humidity` | TINYINT | 50 | 目標温度が前提とする湿度(%) |
| `comfort_adjust_max` | DECIMAL(2,1) | 1.5 | 湿度による目標温度の補正上限(±℃)。0 で補正なし |
| `setpoint_offset` | DECIMAL(2,1) | 2.0 | 設定温度を目標からずらす幅(℃)。0 で目標と同じ |
| `fan_boost_threshold` | DECIMAL(2,1) | 2.0 | 風量を強にする偏差(℃)。中はこの半分 |
| `allowed_modes` | TINYINT | 7 | 許可する運転のビット和(1=冷房 2=ドライ 4=暖房) |
| `fan_speed` | TINYINT | 1 | **NULL 許容に変更。** NULL なら偏差から自動判別 |

## `allowed_modes` の罠

**ゼロ値は「全許可」として扱われる。** 制御ツールの `ModeSet.Allows` が
`s == 0` を「未設定」とみなして全許可を返すためで、これは写し忘れた構築経路が
あってもルールが黙って沈黙しないようにする防御である。

そのため、チェックボックスを全部外して `0` を保存すると、**全部止めたつもりで
全部動く**。この 180° の逆転を UI とスキーマの両方で塞ぐ。

- zod スキーマで `1〜7` に限定し、`0` を弾く
- 画面では全解除時に「少なくとも 1 つ選んでください。全部止めるなら自動制御を
  無効にしてください」と導く

「全部止める」は `enabled` が既に表現しているので、`allowed_modes = 0` に
その意味を持たせる必要はない。

## `fan_speed` の 2 つの「自動」

値 `1` はエアコン自身の自動運転で、`NULL` は制御ツールが偏差から弱・中・強を
決めることを意味する。設定画面で並べると「自動」が 2 つになり紛らわしい。

セレクトの選択肢を 5 つにし、保存値と一対一で対応させる。

| 表示 | 値 |
|---|---|
| 偏差から自動判別 | `NULL` |
| エアコンにまかせる | `1` |
| 弱 / 中 / 強 | `2` / `3` / `4` |

既存の「自動」を「エアコンにまかせる」へ改名して区別する。既存ルールの値は `1`
なので、表示が変わるだけで振る舞いは変わらない。

送信履歴に出るのは実際に送った値（1〜4）だけで `NULL` は現れないため、
`fanSpeedLabel()` は変更しない。

新規ルールの既定は `1`（エアコンにまかせる）のままにする。制御ツール側の DB 既定と
揃え、風量の自動判別はオプトインという方針を崩さないため。

## 入力値の範囲

`AC_LIMITS` に追加する。

| 設定 | 範囲 | 刻み |
|---|---|---|
| 基準湿度 | 1〜99 | 整数 |
| 補正上限 | 0〜5 | 0.5 |
| 設定温度のオフセット | 0〜5 | 0.5 |
| 強風閾値 | 0.5〜5 | 0.5 |
| 許可する運転 | 1〜7 | 整数 |

小数 3 つは既存の `temp_hysteresis` と同じ 0.5 刻みに揃え、刻みの検証も同じ
書き方を使い回す。

強風閾値の下限を 0.5 にしているのは、制御ツールは `0`（常に強）を受け付けるが、
UI がその縮退設定を勧める理由がないため。DB より狭める形になる。

基準湿度を 1〜99 にしているのは、制御ツールがその範囲外を「センサー異常」と
みなして補正を無効化するため。補正を切りたいときは補正上限を 0 にする。

## 設定値どうしの関係の警告

設定を保存はできるが、組み合わせとして意味を成さないものがある。制御ツール側に
この検証は無く、**ダッシュボードが唯一気付ける場所**である。

| 警告 | 出す条件 |
|---|---|
| この組み合わせでは風量「弱」が使われません | 風量が「偏差から自動判別」**かつ** 強風閾値 ≤ 温度の許容幅 × 2 |
| 基準の状態が常にドライ運転の条件を満たします | 補正上限 > 0 **かつ** 湿度上限が設定済み **かつ** ドライが許可済み **かつ** 基準湿度 ≥ 湿度上限 − 湿度の許容幅 |

1 つ目は、冷暖の運転開始に偏差が許容幅を超える必要があり、中に上がる閾値が
強風閾値の半分であることから、`強風閾値 > 許容幅 × 2` でないと弱の段が
到達不能になるため。既定値（強風閾値 2.0・許容幅 1.0）はちょうどその境界にある。

2 つ目は、基準湿度を「その部屋のふだんの湿度」に合わせる運用（制御ツールの
設計書が推奨）に従った結果、湿度上限を超える値にしてしまう誤設定を拾う。

### 前提条件を条件に含める理由

どちらの警告も、**その設定が実際に使われるときだけ**出す。

風量が固定（既定の「エアコンにまかせる」を含む）なら強風閾値は参照されず、
補正上限が 0 なら基準湿度は参照されず、湿度上限が未設定または `allowed_modes` で
ドライを許可していなければドライは動かない。これらを条件に含めないと、
**新規ルールの既定値のままで 1 つ目の警告が出る**（強風閾値 2.0・許容幅 1.0 が
ちょうど境界のため）ほか、ドライを外したルールで「常にドライ運転の条件を
満たします」という成立しない警告が出る。既定で警告が出る状態や成立しない警告は、
利用者に警告を読み飛ばす癖をつけさせるので避ける。

### 置き場所

既存の `humidity_low_warning` はセンサーの実測値が要るためサーバーで計算して
DTO に載せているが、今回の 2 つは**設定値だけで決まる**。入力中にその場で
出せるほうが役に立つので、クライアント側で算出する。

述語は `src/shared/air-conditioner.ts` に純粋関数として置く。共有に置くのは、
`findScheduleOverlaps` が `ac-schedule.ts` にあって `ac-contract.ts` から
使われているのと同じ形。将来サーバー側でも要るようになったら、そのまま使える。

エラーではないので保存は妨げない。

## 画面の構成

入力欄が 12 から 17 に増える。現在の `RuleForm.vue` は `<label>` を平らに
並べた作りで、17 欄が一列に並ぶと一覧性が落ちる。

`<fieldset>` と `<legend>` で 4 つに分ける。**分け方は制御ツール側の設計の核
（部屋の目標と、それを達成するための操作量は別物）と一致させる。** UI 自体が
概念を説明する形になる。

```
基本
  ルール名 / エアコン / センサー

目標と体感（部屋をどうしたいか）
  目標温度 / 基準湿度 ★ / 補正上限 ★
  湿度上限 / 湿度下限
  温度の許容幅 / 湿度の許容幅

操作量（エアコンに何を送るか）
  許可する運転 ★ / 設定温度のオフセット ★
  風量 / 強風閾値 ★

送信の制御
  最短操作間隔 / 再送間隔 / センサー鮮度上限
```

★ が今回の追加。`<fieldset>` / `<legend>` は semantic な HTML なので、
新しい依存も部品も要らない。

## テスト

- `src/shared/ac-contract.test.ts` — `allowed_modes = 0` が弾かれること。
  境界（1 と 7 は通る、8 は弾く）。5 つの範囲と刻み。`fan_speed = null` が通ること
- `src/shared/air-conditioner.test.ts`（新規）— 警告の述語 2 つ。とくに
  **新規ルールの既定値ではどちらの警告も出ないこと**（風量が固定なので
  強風閾値の警告は抑止される）。風量を「偏差から自動判別」にした瞬間に
  1 つ目が出ること。境界（強風閾値 = 許容幅 × 2 ちょうど）で出ること
- `src/server/infrastructure/db/` の既存テスト — 5 列が往復すること。
  `fan_speed = null` が `null` のまま戻ること
- 既存のテストで `fan_speed` を `number` として扱っている箇所の追随

## やらないこと

- **季節プリセット。** 「夏 / 冬」をワンクリックで切り替える UI は見送る。
  チェックボックスと保存値が一対一である利点を優先する。運用して手間だと
  分かってから足せばよい
- **新規ルールの `fan_speed` を NULL にする。** 風量の自動判別を既定にするかは、
  制御ツール側で実測評価が済んでから判断する
- **`allowed_modes` の警告。** 冬に冷房を許可したままにしている、といった
  季節との不整合は、ダッシュボードには季節の概念が無いので判断できない
- **制御ツール側の検証の肩代わり。** ダッシュボードは設定を預かる立場で、
  制御の判断は持たない。この設計書が足す警告は、設定値だけで閉じる関係に限る
